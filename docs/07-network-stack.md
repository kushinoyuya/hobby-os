# ⑦ Ethernet / ARP / IP / ICMP: ping が通る

⑥ では「フレームを1つ送る・受け取る」ができた。ここではその上に層を重ねて、**IP アドレスで相手を指定して通信し、`ping` に答えられる** ようにする。

```
  ⑩ バーチャルホスト   Host ヘッダーで振り分け
  ⑨ HTTP               GET / HTTP/1.1
  ⑧ TCP                つながりを作る
  ⑦ IP / ARP / ICMP    ← ここ。番号で相手を探す、ping
  ⑥ Ethernet フレーム  線の上を流れる「ひとかたまり」
```

## 動かしてみる

### 自作OSから ping を打つ

`make run` で起動して、次を打つ。

```
> ping 10.0.2.2
seq=1 reply from 10.0.2.2 bytes=40 ttl=255 time<10ms
seq=2 reply from 10.0.2.2 bytes=40 ttl=255 time<10ms
seq=3 reply from 10.0.2.2 bytes=40 ttl=255 time<10ms
seq=4 reply from 10.0.2.2 bytes=40 ttl=255 time<10ms
4 sent, 4 received
> arp
  10.0.2.2  52:55:0A:00:02:02
```

答えているのは QEMU の仮想ネットワークのゲートウェイ役。`arp` の表には、ping の前に調べた MAC アドレスが残っている。

### 本物の Linux から自作OSへ ping を打つ

```
make run-ping
```

ターミナルが「実験室」のシェルに変わり、QEMU の画面も開く。OS が起動したら、**ターミナルのほうで** Linux の `ping` を打つ。

```
(ping-lab) $ ping -c 4 10.0.2.15
64 bytes from 10.0.2.15: icmp_seq=1 ttl=64 time=1.73 ms
64 bytes from 10.0.2.15: icmp_seq=2 ttl=64 time=0.648 ms
…
```

**`ttl=64` は、`ip.c` の `IP_TTL` で自分が決めた値**。自作OSが答えている証拠になる。QEMU の画面で `net` を打つと、答えた回数が増えている。終わるときは `exit`。

| コマンド | 見られるもの |
|---|---|
| `ping A.B.C.D` | ping を4回送り、返事を表示する |
| `arp` | 覚えた IP アドレスと MAC アドレスの表 |
| `net` | カードの情報に加えて、IP アドレス、答えた回数、捨てたパケットの数 |
| `netlog on` / `netlog off` | 送受信するフレームを全部16進数で表示する / やめる |

> ⑥ までは届いたフレームを全部表示していたが、今は `netlog on` のときだけ表示する。ping のたびに画面が流れてしまうため。

## 1. 層に分ける

受信するときは下から上へ、見出しを1枚ずつ外しながら渡す。送信はその逆で、上から下へ見出しを足していく。

```
 Ethernet 見出し   IP 見出し       ICMP 見出し   データ
┌──────────────┬───────────────┬────────────┬─────────┐
│ 14 バイト     │ 20 バイト      │ 8 バイト    │ 32 バイト│
└──────────────┴───────────────┴────────────┴─────────┘
│◀──── ethernet.c が読む
               │◀──── ip.c が読む
                               │◀──── icmp.c が読む
```

| ファイル | 層 | 答える問い |
|---|---|---|
| `net.c` | 入口 | 届いたフレームを取り出して、下の層から処理を始める |
| `ethernet.c` | Ethernet | 中身は ARP か IP か? |
| `arp.c` | ARP | この IP アドレスの人の MAC アドレスは? |
| `ip.c` | IP | 自分宛てか? 壊れていないか? 誰に渡せば届くか? |
| `icmp.c` | ICMP | ping の問いかけか、返事か? |

各層は **自分の見出しだけ** を読み、中身は上の層に任せる。⑧ で TCP を足すときも、`ip_input` に振り分けを1つ足すだけで済む。

## 2. ARP: IP アドレスから MAC アドレスを調べる

IP アドレスで相手を指定しても、線の上を流れるフレームに書く宛先は MAC アドレス。だから送る前に調べる必要がある。

```
 hobby-os                                      10.0.2.2
    │ 全員へ「10.0.2.2 の人は MAC を教えて」       │
    │─────────────────────────────────────────────▶│  問い合わせ(操作 = 1)
    │                                             │
    │ 「それは私。MAC は 52:55:0A:00:02:02」       │
    │◀─────────────────────────────────────────────│  返事(操作 = 2)
```

毎回聞くのは無駄なので、答えを **ARP テーブル** に覚えておく(8件。満杯なら順番に上書き)。⑥ の `nettest` は問い合わせを送るだけだったが、今回は **答える側** も作った。外から ping するとき、相手はまず ARP で自作OSの MAC アドレスを聞いてくるので、これに答えないと ping は始まりもしない。

### 誰の情報を覚えるか(`arp_input`)

| 届いた ARP | 覚えるか |
|---|---|
| 自分宛ての問い合わせ・返事 | 覚える。相手も自分と話す気があるので、すぐ使うはず |
| 他人宛てで、送り主がすでに表にある | 更新する。MAC アドレスが変わったのかもしれない |
| 他人宛てで、送り主が表にない | 覚えない。関係ない人で表を埋めないため |
| 送り主の IP が `0.0.0.0` | 覚えない。まだ IP を持っていない人の確認 |

> 問い合わせてきた相手の MAC は覚えたので、その後の ping の返事は改めて ARP を送らずに返せる。

## 3. IP: 受け取るときの検査

ネットワークから届くものは信用しない。**見出しに書いてある長さを信じてメモリを読むと、バッファの外を読んでしまう** ので、順番に確かめて、おかしければ捨てる。

```
ip_input(packet, len)
  │
  ├─ 20バイト未満、または IPv4 でない ─▶ 捨てる
  ├─ 見出しの長さ < 20、全体の長さ < 見出しの長さ、全体の長さ > 届いた長さ ─▶ 捨てる
  ├─ チェックサムが合わない ─▶ 捨てる
  ├─ 宛先が自分でない ─▶ 無視する
  ├─ 分割されたパケットの一部 ─▶ 捨てる(組み立て直す処理を作っていない)
  └─ 種類が ICMP なら icmp_input へ
```

### チェックサム

途中で壊れていないかを調べるための値で、IP と ICMP で同じ計算(`net_checksum`)を使う。

```
 1. 2バイトずつ全部足す(チェックサムの欄は 0 として計算)
 2. 16ビットからあふれた分を、下に足し戻す
 3. 全ビットを反転する → これをチェックサムの欄に書く
```

受け取る側は、チェックサムの欄ごと同じ計算をする。**壊れていなければ結果は 0** になる。

> 例: `0x4500 + 0xFFFF = 0x144FF` → あふれた `1` を足し戻して `0x4500`。

### 全体の長さを信じる理由

Ethernet のフレームは最小 60 バイトなので、短いパケットには後ろに 0 が詰められて届く。だから中身の長さは、届いた大きさではなく **IP 見出しの「全体の長さ」** から求める(その値が届いた大きさを超えていないことは先に確かめてある)。

## 4. IP: 送るときの判断

```
ip_send(宛先 IP, …)
  │
  ├─ 見出しを作る(チェックサムも計算)
  │
  ├─ 宛先は同じネットワーク(10.0.2.x)?
  │     はい   → 宛先本人に渡す
  │     いいえ → ゲートウェイ(10.0.2.2)に渡す    ← ネクストホップ
  │
  └─ 渡す相手の MAC は分かっている?
        はい   → すぐ eth_send
        いいえ → パケットを取っておいて、ARP で聞く
                  ↓ 返事が届いたら(ip_on_arp_learned)
                  取っておいたパケットを送る
```

「同じネットワークか」は、**ネットマスク** `255.255.255.0` で調べる。IP アドレスとマスクの AND が自分と同じなら同じネットワーク。IP パケットの宛先は最終目的地のままで、変わるのは Ethernet の宛先だけ、というのが大事なところ。

> 取っておけるパケットは1つだけで、待っている間に次が来ると古いほうを捨てる。IP はもともと「届かないこともある」しくみなので、これでもよい。困ったら上の層(ping なら次の回、TCP なら再送)が補う。

## 5. ICMP: ping に答える

ping の正体は ICMP の Echo。答えかたは単純で、**種類を 8 から 0 に変えて、そのまま送り返す**。

```
 届いた問いかけ:  08 00 [検査] [id] [seq] [データ]
 返す返事      :  00 00 [検査] [id] [seq] [データ]   ← 検査は計算し直す
```

`id` と `seq` がそのまま返ってくるので、送った側はどの問いかけへの返事か分かる。`netlog on` で確かめられる(`48 53` が id、その次が seq、`61 62 63…` がデータの `abc…`)。

```
TX 74 bytes  52:54:00:12:34:56 -> 52:55:0A:00:02:02  type 0800 (IPv4)
  0020  02 02 08 00 F6 DF 48 53 00 04 61 62 63 64 65 66
RX 74 bytes  52:55:0A:00:02:02 -> 52:54:00:12:34:56  type 0800 (IPv4)
  0020  02 0F 00 00 FE DF 48 53 00 04 61 62 63 64 65 66
```

`0x0022` が ICMP の先頭(14 + 20 = 34 バイト目)。`08` が `00` に変わり、チェックサムが変わり、残りは同じ。

## 6. 外から ping を届ける: 実験室(`tools/ping-lab.sh`)

QEMU の user モードは、**中から外へ** の ping は扱うが、**外から中へ** は通さない。そこで `make run-ping` では tap(仮想の線)で Linux と QEMU を直接つなぐ。

```
 ┌──── 専用のネットワーク空間 ───────────────────────┐
 │  bash / ping                                      │
 │    tap0 (10.0.2.2) ─── 仮想の線 ─── QEMU          │
 │                                     hobby-os      │
 │                                     (10.0.2.15)   │
 └───────────────────────────────────────────────────┘
```

ふつう tap を作るには管理者の権限が要るが、`unshare -r -n` で **自分専用のネットワーク空間(network namespace)** を作り、その中で作れば `sudo` は要らない。Docker のコンテナのネットワークも同じしくみを使っている。空間の外(WSL や Windows のネットワーク)には影響せず、終わると一緒に消える。

### Windows からの ping はやめた

最初の計画は「Windows から ping」だったが、**WSL の Linux からの ping に変えた**。Windows から届けるには、Windows の管理者権限でルーティングを変え、WSL で転送を有効にするなど、OS の外の設定が必要になる。ICMP を学ぶ目的には、本物の `ping` コマンドが答えを受け取れれば十分。

⑨ で Windows のブラウザからページを開く部分は別の話で、QEMU の user モードの **ポート転送(hostfwd)** を使う予定。TCP はこれで外から届くはず(⑨ で確かめる)。

## 7. ブートローダーの修正

カーネルが 15.5KB の上限に近づいたので、読み込める量を 128KB に増やした(`LOAD_SECTORS` = 256)。ただし、数字を変えるだけではうまくいかない。

`int 0x13` に渡す番地は **セグメント:オフセット** で、オフセットは16ビット。今までのように `0x0000:0x7E00` から読むと、32KB 少々でオフセットが 64KB の境目にぶつかる。

```
 番地 = セグメント × 16 + オフセット

 修正後: 32KB ずつに分けて読み、セグメントを進める
   1回目  0x07E0:0000 → 0x07E00 〜
   2回目  0x0FE0:0000 → 0x0FE00 〜     (64 セクタ × 512 ÷ 16 = 0x800 ずつ増える)
   3回目  0x17E0:0000 → 0x17E00 〜
```

オフセットが毎回 0 なので、32KB 読んでも境目にかからない。

合わせて、`kernel/linker.ld` に検査を足した。カーネルと `.bss` の終わりが `0x80000` を超えると、スタックとぶつかる恐れがあるので **リンクの時点でエラーにする**。`Makefile` の 128KB の検査と合わせて、大きくなりすぎても実行前に気づける。

## 8. どう確かめたか

| 確かめたこと | 結果 |
|---|---|
| 自作OS → QEMU のゲートウェイへ ping | 4/4 |
| Linux の `ping` → 自作OS | 4/4、`ttl=64` |
| データの大きさ 0, 1, 55, 1472 バイト(1472 はフレームの最大 1514) | すべて返事あり |
| 1000 バイトの ping を 500 回、5 ミリ秒間隔(受信の輪を何周もさせる) | 500/500 |
| 2000 バイトの ping(分割される) | 捨てる。OS は動き続ける |
| 壊したフレーム 10 種類(チェックサム違い、長さの矛盾、短すぎ、他人宛て、断片など) | どれにも返事をせず、OS も動き続ける |
| IP オプション付き(見出し 24 バイト)の ping | 中身を正しく取り出して返事 |
| 118KB のカーネル(64KB の境界をまたぐ) | 読み込まれたメモリが `kernel.bin` と全バイト一致し、起動する |
| 218KB のカーネル | `make` がエラーで止まる |

## いじってみよう

- `make run-ping` の中で `ping -s 1472 10.0.2.15` と `ping -s 1473 10.0.2.15` を試す。なぜ 1473 で返事が来なくなるのか(1500 - 20 - 8 = 1472)
- `netlog on` にしてから初めての相手に `ping` して、最初に ARP が流れることを見る
- `ip.c` の `IP_TTL` を 32 に変えると、Linux の `ping` の表示はどう変わるか
- `icmp.c` で、返事のチェックサムを計算し直す行を消すと、Linux の `ping` はどうなるか
- 自分自身(`ping 10.0.2.15`)に打つと、なぜタイムアウトするのか(ヒント: 「自分宛てなら自分に戻す」という処理、ループバックを作っていない)
- `build/net.pcap` を Wireshark で開いて、各層の見出しがどう解釈されるか `netlog` の16進数と見比べる

## 補足

- ICMP は Echo だけを扱い、「届かなかった」などの通知(Destination Unreachable)は無視している。TCP / UDP が届いても、まだ何も返さない
- ブロードキャスト宛ての ping には答えない
- 設定(IP アドレスなど)は `net.c` に固定で書いてある。本物の OS は DHCP で受け取る
- 時間の測定はタイマーの 10 ミリ秒単位なので、`time<10ms` や `time=10ms` としか表示できない

## 次: ⑧ TCP

ここまでの層は「届くかどうかは運次第」。TCP はその上に **つながり** を作り、順番どおりに、確実に届くようにする。3ウェイハンドシェイク、シーケンス番号、再送を作り、`ip_input` の振り分けに TCP を足す。
