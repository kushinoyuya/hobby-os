# ⑥ ネットワークカード: PCI と RTL8139 のドライバ

ここで **「ネットワークにフレームを1つ送り、届いたフレームを1つ受け取る」** ところまで作る。Web サーバーへの道のりでいうと、一番下の土台にあたる。

```
  ⑩ バーチャルホスト   Host ヘッダーで振り分け      ← Apache の VirtualHost
  ⑨ HTTP               GET / HTTP/1.1
  ⑧ TCP                つながりを作る
  ⑦ IP / ARP / ICMP    番号で相手を探す、ping
  ⑥ Ethernet フレーム  ← ここ。線の上を流れる「ひとかたまり」を送る・受け取る
```

## 2. PCI: カードを探す(`pci.c`)

### なぜ探す必要があるのか

キーボードはポート `0x60`、PIC は `0x20` のように、昔からある装置は **番号が決まっている**。でもネットワークカードは、どのスロットに挿すか、何枚挿すかがパソコンごとに違う。だから起動したら **「どこに何がつながっているか」を1つずつ聞いて回る**。

### 聞き方

PCI の装置には、それぞれ 256 バイトの **設定空間**(自己紹介の表)がある。これを2つの I/O ポートで読む。

```
 ① 0xCF8 に「どの装置の、表の何バイト目か」を書く
 ② 0xCFC を読むと、その4バイトが返ってくる

 0xCF8 に書く値:
   31     23-16  15-11  10-8   7-0
   [有効]  [バス] [装置] [機能] [表の何バイト目か]
```

設定空間のうち、使ったところ:

| 位置 | 中身 | RTL8139 の場合 |
|---|---|---|
| `0x00` | 作った会社の番号(vendor) | `0x10EC`(Realtek) |
| `0x02` | 製品の番号(device) | `0x8139` |
| `0x04` | 許可のスイッチ(command) | I/O と DMA を許可するビットを立てる |
| `0x0B` | 種類(class) | `0x02`(ネットワーク) |
| `0x10` | BAR0: 窓口の場所 | `0xC001` → I/O ポート `0xC000` から |
| `0x3C` | 使う IRQ | `11` |

BAR0 や IRQ は、**起動時に BIOS が決めて書き込んでおいてくれた** もの。OS はそれを読むだけでよい。

`pci_scan()` はバス 0〜255、装置 0〜31、機能 0〜7 を総当たりで聞き、vendor が `0xFFFF`(誰もいない)でない所を見つける。`pci` コマンドで一覧が見られる。

```
> pci
PCI devices (bus:dev.func  vendor:device  class):
  00:00.0  8086:1237  bridge
  00:01.0  8086:7000  bridge
  00:01.1  8086:7010  storage
  00:01.3  8086:7113  bridge
  00:02.0  1234:1111  display
  00:03.0  10EC:8139  network  <- RTL8139
6 devices
```

> `lspci`(Linux のコマンド)が表示しているのも、この設定空間の中身。

## 3. カードとの2種類のやりとり

| やりとり | 何を | どうやって |
|---|---|---|
| **レジスタ(I/O ポート)** | 「送って」「受信を始めて」という命令、状態の確認 | `io_base + 位置` に `outb` / `inb` |
| **DMA(Direct Memory Access)** | フレームの中身そのもの | カードが **CPU を通さずに** メモリへ直接読み書きする |

1バイトずつ `inb` で受け取ると CPU が忙しくなるので、中身は DMA に任せる。CPU は「どこに置いたか」を教えるだけ。

使ったレジスタ(`io_base` = `0xC000` からの位置):

| 位置 | 名前 | 役割 |
|---|---|---|
| `0x00` | IDR | MAC アドレス(6バイト) |
| `0x10` | TSD0〜3 | 送信の箱 0〜3 の状態。長さを書くと送信が始まる |
| `0x20` | TSAD0〜3 | 送信の箱 0〜3 の番地 |
| `0x30` | RBSTART | 受信の輪の番地 |
| `0x37` | CR | 命令(リセット、送受信の開始)。`BUFE` ビットで「受信の輪が空か」も分かる |
| `0x38` | CAPR | 受信: ドライバがどこまで読んだか |
| `0x3C` | IMR | どの出来事で割り込むか |
| `0x3E` | ISR | 何が起きたか(受信できた / 送信できた / エラー) |
| `0x44` | RCR | どのフレームを受け取るか |

## 4. 初期化の手順(`rtl8139_init`)

```
 1. PCI から 10EC:8139 を探す
 2. BAR0 から I/O ポートの番号、0x3C から IRQ を読む
 3. PCI の command に「I/O ポート許可」「DMA 許可(バスマスタ)」を立てる
 4. 電源を入れて(CONFIG1 = 0)、リセット(CR に RST)→ 終わるまで待つ
 5. MAC アドレスを読む
 6. 受信の輪と送信の箱のメモリを pmm_alloc で借りる
 7. RBSTART に受信の輪の番地を書く
 8. IMR に「受信できた・送信できた・エラー」で割り込むよう書く
 9. RCR に「自分宛て・ブロードキャスト・マルチキャストを受け取る」と書く
10. CR に「送信開始・受信開始」を書く
11. IRQ 11 に割り込みの処理を登録する(④ の irq_register)
```

3 の **バスマスタ** を忘れると、カードはメモリに書き込めず、何も受信できない(QEMU も本物どおりに止める)。

### なぜ kmalloc ではなく pmm_alloc なのか

⑤ のノートでは「受信したパケットの置き場所に kmalloc を使う」と書いたが、実際には **ページ単位の pmm_alloc** にした。

- カードは「番地 X から 9.5KB」のように **ひと続きの場所** にまとめて書き込む。pmm_alloc は連続したページを借りられる
- 受信の輪は大きさ(約 9.5KB)が決まっていて、ずっと使い続ける。細かく借りたり返したりする kmalloc の出番ではない
- ページングを使っていないので、**C から見える番地 = カードに渡す番地**。そのまま渡せる(本物の OS では、ここで番地の変換が必要になる)

kmalloc の出番は、⑦ 以降で「届いたパケットを処理のために取っておく」ときにやってくる。

## 5. 受信: リングバッファ

カードに 8KB の **輪(リングバッファ)** を渡しておくと、届いたフレームを前から順に書き込んでいく。それぞれの前に4バイトの見出しが付く。

```
 rx_buf (0x00110000)
 ┌──────┬─────────────────┬──────┬────────────┬──────┬───── …
 │見出し│ フレーム1        │見出し│ フレーム2   │      │
 └──────┴─────────────────┴──────┴────────────┴──────┴───── …
 ▲                                               ▲
 rx_offset(ドライバが次に読む)                   カードが次に書く
          └──── CAPR で「ここまで読んだ」と伝える

 見出し(4バイト) = 状態(2バイト、ROK ビット)+ 長さ(2バイト、末尾の CRC 4バイト込み)
```

`rtl8139_receive()` の流れ:

1. CR の `BUFE`(空)ビットを見る。空なら「何もない」で終わり
2. `rx_offset` の見出しから長さを読み、中身を写す(CRC の4バイトは外す)
3. `rx_offset` を「見出し + 長さ」だけ進め、**4の倍数に切り上げる**(カードがそう並べる決まり)
4. 8KB を超えたら先頭に戻す(だから「輪」)
5. CAPR に新しい位置を書いて、カードに場所を返す(歴史的な理由で 16 引いた値を書く)

**輪の終わりをまたぐフレーム**: RCR の `WRAP` ビットを立てると、カードは折り返さずに **輪の後ろへはみ出して** 書いてくれる。そのため 8KB + 16 + 1536 バイトを借りておき、読む側は折り返しを気にせず `memcpy` 1回で写せるようにした。

> 確かめ方: `nettest` を140回くり返すと、受信したデータは約10KB になり、8KB の輪を一周する。それでも `net` の errors は 0 だった。

## 6. 送信: 4つの箱

送信には **箱(descriptor)が4つ** あり、0 → 1 → 2 → 3 → 0 … と順番に使う。

```
  箱 i にフレームを写す
        │
  TSAD[i] に箱の番地を書く
        │
  TSD[i] に長さを書く ──▶ カードが DMA で読み出して線に流す
        │                         │
        │                  終わったら TSD[i] の OWN ビットが 1 に
        ▼
  次は箱 i+1 を使う(使う前に OWN = 1 か確かめる)
```

Ethernet には **60バイトより短いフレームは送ってはいけない** という決まりがあるので、ARP(42バイト)は後ろを 0 で埋めて 60 バイトにして送る。受信した返事が 64 バイトで後ろが 0 だらけなのも、同じ理由の詰め物。

## 7. 割り込みの中は短く

```
 カード: 「受信できた」──▶ IRQ 11 ──▶ rtl8139_irq()
                                       ISR を読んで、1 を書き戻す(=「見た」)
                                       数を数える。それだけ
                                             │ CPU が hlt から起きる
                                             ▼
                                kmain のループ: rtl8139_receive() で読み出して表示
```

④ のキーボードと同じ考え方。割り込みは「届いたよ」と CPU を起こすだけで、読み出しや表示はメインのループでする。受信の輪そのものが「割り込みとループの受け渡し場所」になっているので、キーボードのような別のバッファは要らない。

`ISR` は **1 を書いたビットが消える**(write 1 to clear)。消さないと、カードは「まだ見てもらっていない」と思って次の割り込みを出さない。④ の EOI と似ている。

## 8. Ethernet フレームと ARP を読む

`nettest` で送ったフレーム(42バイト)を分解するとこうなる。

```
 ── Ethernet の見出し(14バイト) ──
 FF FF FF FF FF FF   宛先 MAC   全員(ブロードキャスト)
 52 54 00 12 34 56   送り主 MAC 自分
 08 06               中身の種類 ARP(0x0800 なら IPv4)
 ── ARP(28バイト) ──
 00 01               ハードウェア  Ethernet
 08 00               プロトコル    IPv4
 06 04               MAC は6バイト、IP は4バイト
 00 01               操作          1 = 問い合わせ(返事は 2)
 52 54 00 12 34 56   問い合わせた人の MAC
 0A 00 02 0F         問い合わせた人の IP   10.0.2.15
 00 00 00 00 00 00   知りたい MAC          (分からないので 0)
 0A 00 02 02         知りたい人の IP       10.0.2.2
```

返事では操作が `00 02`(返事)になり、「知りたい MAC」だった部分に `52 55 0A 00 02 02` が入って返ってくる。

**ARP は何のため?** IP アドレス(10.0.2.2)だけでは、線の上で誰に渡せばよいか分からない。Ethernet は MAC アドレスで宛先を決めるので、「この IP の人の MAC は?」と全員に聞く。Windows の `arp -a` で見える表は、この答えを覚えておいたもの。

**ネットワークの数は上位バイトが先**(ビッグエンディアン)。x86 は下位バイトが先(リトルエンディアン)なので、`0x0806` を読むときは `read_be16()` で並べ替えている。⑦ 以降、IP や TCP でもずっとついて回る。

## 9. 追加したコマンド

| コマンド | やること |
|---|---|
| `pci` | PCI バスの装置の一覧 |
| `net` | カードの情報(MAC、I/O ポート、IRQ、輪の番地)と、送受信の数 |
| `nettest` | ARP の問い合わせを送り、返事を表示する |

`nettest` 以外でフレームが届いたときも、メインのループが自動で `RX …` と表示する(打ちかけの行は打ち直す)。

## いじってみよう

- `pci` の表示と、QEMU のモニタ(`make run` 中のウィンドウで Ctrl+Alt+2、戻るのは Ctrl+Alt+1)で `info pci` と打った結果を見比べる
- `kernel.c` の `cmd_nettest()` で、知りたい IP を `10, 0, 2, 3`(QEMU の DNS 役)にすると、返ってくる MAC はどうなるか。`10, 0, 2, 99`(誰もいない)ではどうなるか
- `rtl8139.c` の手順 3 で `PCI_CMD_BUS_MASTER` を外すと、`nettest` はどうなるか
- `build/net.pcap` を Windows の Wireshark で開いて、同じフレームが記録されているか見る(エクスプローラーで `\\wsl.localhost\Ubuntu\home\(ユーザー名)\hobby-os\build` を開く)

## 補足

- カードは自分宛て・ブロードキャスト・マルチキャストだけを受け取る。RCR の AAP ビットを立てると、他人宛ても全部受け取る(プロミスキャスモード。Wireshark が使うもの)
- 受信の見出しが壊れていたら、溜まっていた分を捨ててカードが書いている位置から読み直す。手抜きだが、QEMU では起きない
- カーネルは約13KB になり、上限の 15.5KB(`LOAD_SECTORS` = 32)に近づいた。⑦ ではブートローダーの読み込み量を増やす必要がある(1回の `int 0x13` で 64KB の境目をまたげない点に注意)
