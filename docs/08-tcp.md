# ⑧ TCP: 確実な「つながり」を作る

⑦ までの IP は、パケットが届かなくても、順番が変わっても、重複しても何もしない。その上に **順番どおりに、抜けなく届く通信路** を作るのが TCP。Web サーバー(⑨)はこの上に載る。

```
  ⑩ バーチャルホスト   Host ヘッダーで振り分け
  ⑨ HTTP               GET / HTTP/1.1
  ⑧ TCP                ← ここ。つながりを作る
  ⑦ IP / ARP / ICMP    番号で相手を探す、ping
  ⑥ Ethernet フレーム  線の上を流れる「ひとかたまり」
```

作ったのは **待ち受ける側(サーバー)だけ**。自分からつなぎに行く機能は、ゴールの Web サーバーには要らないので作っていない。

## 動かしてみる

OS は起動すると、ポート 7 で **エコーサーバー**(受け取ったものをそのまま返す)を動かす。

```
make run-ping
```

ターミナルが実験室のシェルに変わる。OS が起動したら、まず QEMU の画面で `tcp log on` と打ち、ターミナルから本物の Linux の `nc` でつなぐ。

```
(ping-lab) $ printf hi | nc -N 10.0.2.15 7
hi
```

`hi` が返ってくる。答えているのは自作OS。

| コマンド | 見られるもの |
|---|---|
| `tcp` | つながりの一覧と、送受信・再送などの回数 |
| `tcp log on` / `tcp log off` | 流れるセグメントと状態の変化を表示する / やめる |
| `tcp drop N` | 送受信とも N 個に1個わざと落とす(`0` でやめる)。落としたものは `RX!` `TX!` と赤く出る |
| `tcp isn N` | 次のつながりの最初の番号を N にする |
| `echo on` / `echo off` | エコーサーバーを動かす / 止める |

`make run` のときは、Linux や Windows の `127.0.0.1:7777` からポート 7 へつながる(11 節)。

## 2. 3ウェイハンドシェイク: なぜ3回か

お互いに **「自分はこの番号から数え始める」と伝えて、相手に確認してもらう** 必要がある。方向が2つあるので本来は4回だが、真ん中の2つを1回にまとめて3回になる。

| | 内容 | 確かめられること |
|---|---|---|
| ① SYN | 私は 565 から数えます | |
| ② SYN+ACK | 566 を待ちます(ack)。私は 1107500 から数えます | 相手の番号が伝わった |
| ③ ACK | 1107501 を待ちます | 自分の番号も伝わった |

**SYN は番号を1つ消費する**。ログでも、`seq=...565` の SYN の次のデータは `566` から始まっている。

最初の番号(ISN)を毎回変えるのは、前のつながりから遅れて届いた迷子と混ざらないようにするため。`choose_isn` の作り方はタイマーと回数から計算するだけで **推測できる**。本物の OS はハッシュで推測できないようにしている(番号が読まれると、なりすましてデータを差し込まれるおそれがある)。このままインターネットへ出してはいけない理由の1つ。

### MSS: 1回に運べる量

SYN の見出しの後ろに「オプション」として、受け取れる最大のデータ量を伝え合う。Ethernet の 1500 バイトから IP 20、TCP 20 を引いた **1460**。相手の値より大きく送らない。オプションがなければ決まりの 536 を使う。

## 3. seq と ack: 1バイトごとの番号

TCP はパケットではなく **データの1バイトごとに番号を振る**。

```
 seq=566, len=2  →  "h" が 566 番、"i" が 567 番
 ack=568         →  「567 番まで全部受け取った。次は 568 番が欲しい」
```

ack は「ここまで全部」という意味(**累積確認応答**)なので、途中の ACK が失われても、後の ACK が代わりになる。

送る側のバッファと番号の関係は次のとおり(`tcp.c` の先頭にも同じ図がある)。

```
      snd_una          snd_nxt
         │  送ったが      │  まだ送って
         │  ACK がまだ    │  いない
         ▼                ▼
         ├────────────────┼───────────┤
         │◀──────── tx_len ──────────▶│
```

ACK が来たら `snd_una` を進めて、その分をバッファから消す。**ACK が来るまで消さない** のが再送できる理由。

### 番号の比較は引き算で

番号は 32 ビットなので、4GB で 0 に戻る。だから `a < b` では比べられない。

```
 a = 0x00000010, b = 0xFFFFFFF0

 普通に比べる:    a < b                       ← 間違い(a のほうが「後」)
 引き算して符号付きで見る: (int32_t)(a - b) = 0x20 > 0  ← 正しい
```

`SEQ_LT` などのマクロがこれをやっている。`tcp isn 4294960000` で実際に試せる。

## 4. 受け取るときの判断

⑦ の `ip_input` と同じで、届いたものは信用しない。`tcp_input` はまず見出しの長さを確かめ、チェックサムを見て、つながりを探す。

TCP のチェックサムには **疑似ヘッダー**(送り主 IP、宛先 IP、種類、長さ)も足す。IP の見出しが途中で壊れて別の相手に届いても気づけるようにするため。

つながりが見つかったら `input_conn` が順番に調べる。

```
input_conn
  ├─ 同じ SYN がまた来た(SYN_RECEIVED) ─▶ SYN+ACK を送り直す
  ├─ RST ─▶ 番号がぴったりなら閉じる / 範囲内なら ACK を返す / 範囲外は無視
  ├─ SYN(つながっているのに) ─▶ ACK を返す。閉じない
  ├─ ACK が付いていない ─▶ 捨てる
  │
  ├─ 番号を確かめる
  │    ├─ 全部受け取り済み ─▶ ACK を返す(相手に ACK が届かなかったのだろう)
  │    ├─ 前半だけ受け取り済み ─▶ その分を切り落とす
  │    └─ 間が抜けている ─▶ 捨てて「欲しいのはまだこの番号」と ACK を返す
  │
  ├─ input_ack:  ACK を処理する(送信バッファを空ける、ウィンドウを覚える)
  ├─ store_data: データを受信バッファへ
  ├─ input_fin:  FIN を処理する
  └─ tcp_output: 送れるものがあれば送る
```

### RST を番号で確かめる理由

RST を受け取るとつながりは即座に切れる。番号を確かめないと、他人が偽の RST を1つ送るだけで切断できてしまう。そこで **番号がぴったりのときだけ信じる**(RFC 5961)。ずれていて範囲内なら ACK を返す。本物の相手なら、その ACK の番号で RST を送り直せる。

## 5. 再送: 届かなかったら送り直す

ACK が来ないまま時間が過ぎたら、`snd_una` からのデータを全部送り直す。待ち時間は **再送のたびに 2 倍** にする(指数バックオフ)。混んでいるときに追い打ちをかけないため。

```
 時刻(秒)  0    0.5   1.5   3.5   7.5   15.5   31.5   47.5
            送信  再送1 再送2 再送3 再送4 再送5  再送6  あきらめて RST
```

SYN+ACK の再送は 4 回まで(約 15.5 秒)。短くしているのは、SYN だけ送って放置する相手に表の行を占領させないため。

`tcp_tick` がこの時計を見ている。`net_poll` の中で呼ぶので、何も届かなくても 10 ミリ秒ごとに調べられる。

> 本物の OS は実際の往復時間(RTT)を測って待ち時間を決める。ここでは 0.5 秒に固定している。

### 高速再送: 時間切れを待たない

順番が飛んだセグメントを受け取った相手は、同じ ACK を返してくる。**同じ ACK が 3 回続いたら**、「後ろは届いているのに先頭だけ抜けている」と判断して、時間切れを待たずに先頭を送り直す。

```
 送信:   1  2  3  4  5
            ✕
 ACK:    2  2  2  2     ← 3 が届くたびに「欲しいのは 2」が続く
                 ↑ 同じ ACK が3回続いた → すぐ 2 を送り直す
```

### 順番の飛んだデータは捨てている

本物の TCP は後ろのデータを取っておくが、ここでは **捨てて、ACK を返すだけ** にした(保管すると穴の管理が要る)。相手が送り直してくれるので正しさは変わらず、落ちたときに少し遅くなるだけ。

## 6. フロー制御: 相手の受信バッファをあふれさせない

ACK には **ウィンドウ** が付いている。「受信バッファがあと何バイト空いているか」。送る側は、未確認のデータがこれを超えないように送る。

ログの `win=` を見ると分かる。

```
RX ... PSH,ACK len=2                      "hi" が届いて受信バッファに入った
TX ... ACK ... win=4094                   4096 - 2 = 4094
TX ... PSH,ACK ... win=4096 len=2         エコーサーバーが読んだので、また 4096
```

### ウィンドウが 0 になったら

相手のウィンドウが 0 だと送れない。後で「空いた」という ACK が来るはずだが、**ACK は再送されないので、失われると永久に止まる**。そこで時々 **1 バイトだけ送って様子を見る**(ウィンドウプローブ)。`tcp_tick` の `snd_nxt == snd_una` の分岐がこれ。

相手がウィンドウ 0 のまま ACK を返してくる間は、生きている証拠なので再送の失敗に数えない。

エコーサーバーも、送信バッファに入る分しか読まない。だから大量に送り続けると、

```
 相手が受け取らない → 送信バッファが満杯 → エコーサーバーが読まない
   → 受信バッファが満杯 → ウィンドウが 0 → 相手が送るのをやめる
```

と、後ろへ順に伝わる(自動テストの `test_flow_control_closes_and_reopens_window` で、8192 + 4096 バイトで止まることを確かめている)。

## 7. 切断: なぜ4回か

TCP は **方向ごとに別々に閉じる**。FIN は「こちらから送るものはもうない」という意味で、受け取るのは続けられる。ログでも、`nc` が FIN を出した後に、自作OSがエコーのデータを送っている。これがハーフクローズ。

FIN も番号を1つ消費する。ログの `ack=1107503`(データの ACK)と `ack=1107504`(FIN の ACK)の違いがそれ。

## 8. 状態遷移

作ったものの全体図。自分からつなぎに行かないので、`LISTEN` は「待ち受けの表にポートがある」ことで表し、行は SYN が来てから作る。

```
                     SYN を受け取る
  (待ち受け) ─────────────────────▶ SYN_RECEIVED
                                       │ ACK を受け取る
                                       ▼
                ┌────────────────── ESTABLISHED ──────────────────┐
  アプリが閉じる │                                                 │ 相手の FIN
   FIN を出す   ▼                                                 ▼
           FIN_WAIT_1                                         CLOSE_WAIT
            │        │ 相手の FIN                                 │ アプリが閉じる
     ACK    │        ▼                                            ▼  FIN を出す
            │     CLOSING                                       LAST_ACK
            ▼        │ ACK                                        │ ACK
           FIN_WAIT_2│                                            ▼
            │        │                                          CLOSED
  相手の FIN ▼        ▼
           TIME_WAIT ── 時間切れ ──▶ CLOSED
```

### TIME_WAIT: なぜすぐ消さないか

最後の ACK が失われると、相手は FIN を送り直してくる。つながりを消してしまっていると、答えられない。また、同じ番号の組で新しくつないだときに、古いつながりの迷子が混ざるおそれもある。

本物の OS は 60 秒ほど残すが、**表が 8 行しかないので 4 秒にした**。行が足りなければ TIME_WAIT の行から再利用する。

> **先に閉じた側に TIME_WAIT が残る**。⑨ で Web サーバーが先に閉じると、行がここで埋まりやすい。

### 行が空かない場合への備え

| 状況 | 対応 |
|---|---|
| SYN だけ送って放置 | SYN+ACK を 4 回送り直してあきらめる |
| 表が満杯のときの SYN | 黙って捨てる。相手が送り直す頃には空いているかもしれない |
| FIN_WAIT_2 のまま相手が FIN を出さない | 30 秒で見切る |
| 相手が消えた(データの ACK が来ない) | 再送 6 回であきらめて RST |

## 9. アプリとの関係

OS にはまだプロセスがないので、**待たずにすぐ戻る関数** を、メインのループから呼び続ける形にした。`echo.c` が見本で、⑨ の Web サーバーも同じ形で作る。

```
 メインのループ
   ├ キーボード
   ├ net_poll()   届いたフレームを処理する → tcp_input → 受信バッファへ
   │                                       → tcp_tick(再送の時計)
   ├ echo_poll()  tcp_accept / tcp_recv / tcp_send / tcp_close
   └ cpu_halt()   次の割り込みまで休む
```

| 関数 | 役目 |
|---|---|
| `tcp_listen(port)` | ポートを待ち受ける |
| `tcp_accept(port)` | つながった相手を1つ受け取る。いなければ -1 |
| `tcp_recv(id, buf, size)` | 読む。まだなければ 0、相手が閉じたなら -1 |
| `tcp_send(id, data, len)` | 送信バッファに入れる。入った分のバイト数を返す |
| `tcp_close(id)` | 残りを送ってから FIN を出す |

Linux のソケット(`listen` / `accept` / `recv` / `send` / `close`)とほぼ同じ形になっている。

## 10. どう確かめたか

### Python が相手役のテスト(`make test-tcp`、約3分、39 件)

本物の Linux は行儀がよいので、順番の入れ替えや ACK の無視は簡単に起こせない。そこで QEMU の仮想の線(`-netdev socket`)を Python につなぎ、フレームを手で組み立てて送る。OS が送ったチェックサムも毎回検査する。

| 分類 | 確かめたこと |
|---|---|
| ハンドシェイク | MSS を伝え合う、MSS より大きく送らない、SYN の重複、間違った ACK には RST |
| データ | エコー、壊れたチェックサムは無視、重複を二重に返さない、順番の飛び、一部の重なり |
| 再送 | 間隔が 0.5 / 1 / 2 秒と延びる、ACK で止まる、同じ ACK 3 回で高速再送、再送 6 回であきらめる |
| フロー制御 | ウィンドウ 0 でプローブ、再送の上限を超えても切らない、12288 バイトで閉じて、開くと全部届く |
| RST / 迷子 | 閉じたポート、迷子の ACK、番号がぴったり / 範囲内 / 範囲外の RST、つながっているのに来た SYN |
| 切断 | 相手から / こちらから / 同時に閉じる、データと FIN が同時、TIME_WAIT の動き、FIN の再送 |
| 番号の一周 | 相手の番号、自分の番号 |
| 異常な入力 | 見出しの長さの矛盾、長さ 0 のオプション、表が満杯、SYN を 30 個、でたらめなセグメント 4000 個とフレーム 2000 個 |

このテストで見つかったバグ: ウィンドウが開いても、受け取ってもらえなかったプローブの再送を延びきった時計のまま待っていて、最大 16 秒止まっていた。今はウィンドウが開いた時点で送り直す。

### 本物の Linux とのテスト(`make test-tcp-linux`)

`nc` でランダムなデータを送り、返ってきたものを比べた。

| 確かめたこと | 結果 |
|---|---|
| 1 MB の往復 | 全バイト一致、1.3 秒 |
| 4 本同時に 200 KB ずつ | 全バイト一致 |
| `tcp drop 7` で 200 KB | 全バイト一致、約 10 秒(再送の分だけ遅い) |
| `tcp isn 4294960000` で 100 KB | 全バイト一致。記録(pcap)で番号が 0 を越えたことも確認 |
| 閉じたポート | 断られる |

## 11. Windows から TCP が届くか(⑨ の準備)

`make run` の設定に、QEMU の **ポート転送(hostfwd)** を足した。

```
 Windows ─▶ 127.0.0.1:7777 ─▶ WSL の QEMU ─▶ hobby-os のポート 7
```

QEMU を動かしたまま Windows 側の PowerShell の TCP クライアントからつなぎ、`from-windows` が返ってくることを確かめた。**ブラウザで試すには HTTP(⑨)が要る** が、途中の経路は通っている。

> `127.0.0.1` にだけ開いているので、同じネットワークの他の PC からはつながらない。

ポート転送があるのは `make run` のときだけ。実験室(`make run-ping`)では 7777 を使わず、中のシェルから `10.0.2.15` のポート 7 へ直接つなぐ。

## いじってみよう

- `tcp log on` にして `nc 10.0.2.15 7` でつなぎ、1行打つごとに何が流れるか、1 節の図と見比べる
- `echo off` の後に `nc` でつなぐと、なぜすぐ `Connection refused` になるのか(ログに何が流れるか)
- つないだまま `echo off` すると、状態はどう変わるか。`tcp` を何度か打って TIME_WAIT が消えるのを見る
- `tcp drop 3` で `tcp log on` にして、`RX!` `TX!` の後に何が起こるか追う
- `tcp isn 4294967290` の後につないで、`seq` が 0 に戻るところを見る
- `tcp.c` の `RTO_INITIAL` を変えると、`tcp drop` のときの転送時間はどう変わるか
- `tcp.c` の `DUP_ACK_LIMIT` を大きくして高速再送を効かなくすると、`make test-tcp-linux` の `drop` はどのくらい遅くなるか
- `TCP_RX_BUF` を 1024 にすると、ログの `win=` や転送速度はどう変わるか

| 作っていないもの | 本物では | ここで困らない理由、困るとき |
|---|---|---|
| 自分からつなぐ(SYN_SENT) | クライアントに必要 | Web サーバーには要らない |
| 順番の飛んだデータの保管 | 取っておいて穴だけ埋める | 落ちたときに遅くなるだけ |
| **輻輳制御** | ネットワーク全体を詰まらせないよう、送る量を徐々に増やす | 仮想の線 1 本なので困らない。**インターネットに出してはいけない最大の理由** |
| RTT の測定 | 待ち時間を実測で決める | 0.5 秒固定で足りる |
| Nagle、遅延 ACK | 小さなセグメントや ACK をまとめて減らす | ムダはあるが正しさは変わらない |
| ウィンドウスケール、SACK、タイムスタンプ | 速い回線や、落ちたときの回復を効率化する | 受信バッファが 4KB なので要らない |
| キープアライブ、放置したつながりの片付け | 相手が黙って消えたことに気づく | **⑨ で必要になるかも**。何も送らないまま相手が消えると、行が空かない |
| 推測されない最初の番号 | ハッシュで作る | 実験用の閉じたネットワークの中だけで使う |
| 読み残したまま閉じたときの RST | 相手に RST で知らせる | 黙って捨てている |
