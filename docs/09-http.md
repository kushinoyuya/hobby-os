# ⑨ HTTP サーバー: TCP の上で「テキストの手紙」をやり取りする

⑧ で作った TCP は、バイトの列を順番どおりに届けるだけ。そこにどんな意味を持たせるかを決めるのが **HTTP**。⑨ では、自作OSの上で Web サーバーを動かし、**Windows のブラウザから自作OSのページを開く**。

```
  ⑩ バーチャルホスト   Host ヘッダーで振り分け
  ⑨ HTTP               ← ここ。GET / HTTP/1.1
  ⑧ TCP                つながりを作る
  ⑦ IP / ARP / ICMP    番号で相手を探す、ping
  ⑥ Ethernet フレーム  線の上を流れる「ひとかたまり」
```

作ったのは HTTP/1.1 の **GET と HEAD だけ**。ファイルシステムがまだないので、返すページはプログラムの中に持っている。

## 動かしてみる

```
make run
```

QEMU の画面に `HTTP     : web server on port 80 ... ok` と出たら、**Windows のブラウザで `http://localhost:8080/` を開く**。

```
 ブラウザ ─▶ localhost:8080 ─▶ WSL の QEMU(hostfwd)─▶ hobby-os のポート 80
```

| パス | 中身 |
|---|---|
| `/` | トップページ。届いた Host ヘッダー、相手の IP とポート、何回目のリクエストかなどを表示する |
| `/hello.txt` | `Hello from hobby-os!` の1行 |
| `/big` | 64 バイトの行が 1024 行(64KB)。TCP の送信バッファ(8KB)より大きい応答の確認用 |
| それ以外 | 404 Not Found |

QEMU の画面には、リクエストのたびに1行出る(アクセスログ)。

```
HTTP 10.0.2.2:36844 GET / host=localhost:8080 -> 200 (829 bytes)
HTTP 10.0.2.2:36848 GET /hello.txt host=127.0.0.1:8080 -> 200 (21 bytes)
HTTP 10.0.2.2:36850 GET /nothing host=127.0.0.1:8080 -> 404 (74 bytes)
```

> ブラウザで開くと、頼んでいない `GET /favicon.ico -> 404` も出るはず。ブラウザがタブのアイコンを探しに来ている。

| コマンド | 見られるもの |
|---|---|
| `http` | 受け付けたつながり、リクエストの数(2xx / 4xx / 5xx 別)、keep-alive で使い回した回数、時間切れ |
| `http log on` / `http log off` | アクセスログを出す / やめる(起動時は on) |
| `http on` / `http off` | Web サーバーを動かす / 止める |

実験室(`make run-ping`)の中からは `curl -v http://10.0.2.15/` でつながる。`-v` を付けると、送ったリクエストと届いた応答の見出しが全部見える。

## 1. 手紙の形

HTTP は **人が読めるテキスト** でやり取りする。`curl -v http://10.0.2.15/hello.txt` で流れるものは、ほぼこのまま。

```
GET /hello.txt HTTP/1.1          ← リクエスト行: メソッド パス バージョン
Host: 10.0.2.15                  ← ヘッダー: 名前: 値
User-Agent: curl/8.x
Accept: */*
                                 ← 空行。ここで見出しが終わる
```

```
HTTP/1.1 200 OK                  ← ステータス行: バージョン 番号 理由
Server: hobby-os
Content-Type: text/plain; charset=utf-8
Content-Length: 21               ← 本文が何バイトあるか
Connection: keep-alive           ← この後もつながりを使い続けてよい
                                 ← 空行
Hello from hobby-os!             ← 本文(ちょうど 21 バイト)
```

- 行の区切りは `\r\n`(CRLF)。`\n` だけの行も受け付けている
- **見出しの終わりは空行** で分かる。だから「空行が来るまで ためる」のがサーバーの最初の仕事
- **本文の終わりは Content-Length** で分かる。TCP はただのバイトの列で、「ここで1通終わり」という区切りを持たないため

### ステータス番号

| 番号 | 意味 | このサーバーで返すとき |
|---|---|---|
| 200 | OK | 見つかった |
| 400 | Bad Request | リクエストの形が壊れている(下の 4 節) |
| 404 | Not Found | そのパスはない |
| 405 | Method Not Allowed | 知っているメソッドだが使えない(POST など)。`Allow: GET, HEAD` を付ける |
| 408 | Request Timeout | 見出しの途中で止まった |
| 414 | URI Too Long | パスが 256 バイト以上 |
| 431 | Request Header Fields Too Large | 見出しが 2048 バイトに収まらない |
| 501 | Not Implemented | 知らないメソッド(`BREW` など) |
| 505 | HTTP Version Not Supported | `HTTP/2.0` など |

百の位で大まかに分かる: **2xx は成功、4xx は頼んだ側の間違い、5xx は答える側の都合**。

## 2. つながりごとの流れ

`http.c` は `echo.c` と同じく、メインのループから `http_poll()` を呼んでもらい、待たずにすぐ戻る。つながりごとに「今どこまで進んだか」を覚えておく。

```
            tcp_accept
                │
                ▼
   ┌──────▶ READING ─── 空行まで届いた ──▶ リクエストを読み解いて応答を作る
   │        (ためる)                              │
   │           │ 10 秒たっても空行が来ない → 408   ▼
   │           │ 2048 バイトで満杯 → 431       SENDING
   │           │ 相手が閉じた → 閉じる       (送信バッファに入るだけ入れる)
   │                                               │
   │                               ┌───── 全部入れた
   │                               ▼
   └── keep-alive なら ◀── 続ける? ── 続けないなら tcp_close(FIN)
       (5 秒で次が来なければ閉じる)
```

| 関数 | 役目 |
|---|---|
| `read_more` | 届いた分を `req` にためる |
| `find_head_end` | 空行を探す。見つかれば見出しの終わりの位置 |
| `parse_request` | リクエスト行とヘッダーを読み解く。だめならエラーの番号を返す |
| `handle_request` | 何を返すか決め、続けるか決め、応答の見出しと本文を用意する |
| `push_response` | 見出しと本文を 1460 バイトずつ `tcp_send` に渡す |
| `serve` | 上の図の状態を進める |

### 送信バッファより大きい応答

TCP の送信バッファは 8KB なので、64KB の `/big` は一度に入らない。`push_response` は **入るだけ入れて、残りは覚えておき、次の `http_poll` で続きを入れる**。相手が ACK を返すとバッファが空き、また入る。

`/big` の中身はメモリに置かず、送る直前に何バイト目かから計算して作っている(`fill_big`)。メモリが 64KB 要らない。

## 3. keep-alive: 1つのつながりを使い回す

TCP のつながりを作るにはハンドシェイクで往復が要る。ページ1つに画像が 10 個あれば、毎回つなぎ直すのはムダ。そこで HTTP/1.1 では **応答の後もつながりを閉じないのが標準** になった。

| | 何も書かないと | 書けば変わる |
|---|---|---|
| HTTP/1.0 | 1回で閉じる | `Connection: keep-alive` で続ける |
| HTTP/1.1 | 続ける | `Connection: close` で閉じる |

続けられるのは、**Content-Length で応答の終わりが分かる** から。これがないと、受け取る側は「つながりが閉じたら終わり」としか判断できない。

**パイプライン**: 応答を待たずに次のリクエストを送ってくる相手もいる。`req` に残った分を次の見出しとして読むので、順番どおりに答えられる(テストで確認)。

**こちらから閉じるとき**:
- 形の壊れたリクエストの後(どこから次のリクエストか信用できない)
- 本文付きのリクエスト(POST など)の後。本文を読んでいないので、残りが次のリクエストに見えてしまう
- 1つのつながりで 100 回応答した後

## 4. Host ヘッダー: ⑩ への入り口

HTTP/1.1 では **Host ヘッダーが必須**。ないと 400 を返す。

1つの IP アドレスで何個もサイトを動かすとき、TCP の段階では「10.0.2.15 のポート 80 に来た」ことしか分からない。どのサイト宛てかは、**手紙の中の `Host:` を読むまで分からない**。

```
GET / HTTP/1.1
Host: blog.example.test        ← これを見て、どのサイトのページを返すか決める(⑩)
```

トップページに届いた Host を表示しているので、curl の `-H "Host: なんでも"` で変えると、ページの表示が変わるのが見られる。

Host を2つ書いてくるリクエストも 400 にしている。サーバーと途中の中継役が別々の Host を信じると、思わぬサイトに届いてしまうため。

### 相手から来た文字列は信用しない

トップページには届いた Host をそのまま表示している。ここで `Host: <script>…</script>` を **そのまま HTML に入れると、そのプログラムがページの中で動いてしまう**(XSS)。`put_html` で `<` を `&lt;` などに置き換え、ただの文字として表示させている。

QEMU の画面に出すときも、制御文字は `?` にし、長すぎる分は切っている(`print_untrusted`)。画面を乱されないため。

### 厳しく断っている形

| 形 | 返すもの |
|---|---|
| `Host : a`(名前と `:` の間に空白) | 400 |
| 行頭が空白の行(昔の「前の行の続き」) | 400 |
| `GET  / HTTP/1.1`(空白が2つ) | 400 |
| `GET http://a/ HTTP/1.1`(URL まるごと) | 400(作っていない) |

どれも、**読む側によって解釈が分かれる** 形。中継役とサーバーで読み方が違うと、片方を素通りしたリクエストがもう片方で別物になる(リクエストスマグリング)。迷う形は受け付けないのが安全。

## 5. 時間切れ: 黙った相手に行を占領させない

⑧ のやり残し(「何も送らないまま消えた相手のつながりは行を占領し続ける」)への答え。TCP の行は 8 つしかなく、エコーサーバーと分け合っている。

| いつ | どれだけ待つ | どうする |
|---|---|---|
| つないだのに何も来ない | 10 秒 | 黙って閉じる |
| 見出しの途中で止まった | 最初の1バイトから 10 秒 | 408 を返して閉じる |
| keep-alive で次を待つ | 5 秒 | 黙って閉じる |
| 応答を受け取ってくれない(ウィンドウが 0 のまま) | 少しも進まずに 30 秒 | **RST** で打ち切る(`tcp_abort`) |

見出しの持ち時間を「最後に届いてから」ではなく **「最初の1バイトから」** 数えているのは、1バイトずつゆっくり送って行を占領し続ける攻撃(Slowloris)を防ぐため。

最後の行だけ RST なのは、FIN では終われないから。ウィンドウが 0 の相手には、送信バッファに残ったデータが先に届かないと FIN を送れない。そのため ⑧ の TCP に、アプリから RST で切る `tcp_abort` を足した。

## 6. どう確かめたか

### `make test-http`(約 2 分、30 件)

実験室の中で、本物の curl と、Python で手で組み立てたリクエストを送る。

| 分類 | 確かめたこと |
|---|---|
| curl | `/` に Host が表示される、`/hello.txt`、`/big` が 64KB 全バイト一致、404、HEAD の Content-Length |
| keep-alive | curl が2つの URL で同じつながりを使い回す、HTTP/1.0 は閉じる / Keep-Alive と書けば続く |
| 同時 | 6 本同時に `/big`(ブラウザは1つのサイトに最大 6 本つなぐ) |
| パイプライン | 2つ続けて送ると順番どおりに2つ返る。HEAD の後に本文が混ざらない |
| 寛容さ | `\n` だけの行、リクエストの前の空行 |
| XSS | Host に入れた `"><b>&` がエスケープされる |
| 壊れた形 | 上の表の 400 たち、505、405(閉じる / 閉じない)、501、414、431 |
| 時間切れ | 何も送らない → 約 10 秒で閉じる、見出しの途中 → 約 10 秒で 408、keep-alive → 約 5 秒で閉じる、読まない相手 → 約 30 秒で RST |

⑧ の `make test-tcp`(39 件)と `make test-tcp-linux` も、⑨ の変更の後に全部通ることを確かめた。`test-tcp-linux` の「閉じたポート」の例は、80 が開いたので 81 に変えた。

### 転送経由

`make run` と同じ設定で起動し、WSL から `127.0.0.1:8080` に curl でつないで、200 と 404 が返り、QEMU の画面にアクセスログが出ることを確かめた。

**Windows のブラウザで開くのは、まだ試していない**。⑧ で同じ転送のしくみ(7777 番)が Windows から通ることは確かめてあるので、開けるはず。最初にやってみてほしい。

### 相手の IP が 10.0.2.2 になる

トップページの「あなたの IP」は、Windows から開いても `10.0.2.2` になる。QEMU の user モードは **中継役(NAT)** で、外からの接続を自分の番号に付け替えて中へ渡すため。本物の Web サーバーでも、前に中継役(ロードバランサーなど)がいると同じことが起き、`X-Forwarded-For` ヘッダーで元の番号を伝えてもらう。

## いじってみよう

- ブラウザで開いてから `http` を打つ。リクエストの数と「keep-alive で使い回した回数」はいくつになったか。ブラウザで再読み込みすると増え方はどう変わるか
- `tcp` を打って、ブラウザが何本つないでいるか見る。5 秒後にもう一度打つとどうなっているか
- 実験室から `curl -v -H "Host: <b>hi</b>" http://10.0.2.15/`。ページのソースで Host がどう書かれているか
- 実験室から `nc 10.0.2.15 80` でつなぎ、手で `GET / HTTP/1.1` と `Host: a` と空行を打つ。何も打たずに 10 秒待つとどうなるか
- `tcp log on` にして `curl http://10.0.2.15/big` を取る。応答がいくつのセグメントに分かれ、ウィンドウがどう動くか
- `http.c` の `IDLE_TICKS` を 1 秒にすると、ブラウザの再読み込みで `connections` の増え方はどう変わるか
- `put_html` を `put_str` に置き換えて、上の `<b>hi</b>` を試す(試したら戻す)

## 補足: 作っていないもの

| 作っていないもの | 本物では | ここで困らない理由、困るとき |
|---|---|---|
| リクエストの本文(POST) | フォームの送信などで使う | GET だけで足りる。本文付きは閉じて終わる |
| chunked 転送 | 長さが先に分からない応答を小分けで送る | 応答の長さはいつも先に分かっている |
| ファイルを読んで返す | ディスクのファイルを返す | ファイルシステムがない。ページはプログラムの中にある |
| `Date` ヘッダー | 応答に付けるべきもの | 時計(RTC)を読んでいない |
| Range、圧縮、キャッシュの確認(304) | 速くするしくみ | 正しさは変わらない |
| HTTP/2、HTTPS(TLS) | 今のふつうの Web | 暗号の実装は大仕事。実験用の閉じたネットワークだけで使う |
| `http://host/path` の形のリクエスト | 中継役(プロキシ)宛てに使う | ブラウザがサーバーへ直接送るときは使わない |
